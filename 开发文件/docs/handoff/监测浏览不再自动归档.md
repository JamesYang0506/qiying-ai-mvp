# 监测浏览不再自动归档

日期：2026-10-17

## 原因

之前 GET `/api/import-v1/monitor` 调用了 `monitor.create()`。每次打开页面、刷新或切换筛选，都产生全新的视图和快照编号，并把分析结果、依据和输入引用保存到 `data/imports/monitor-state`。数据没有变化也会再次归档，因此目录随查看次数增长。

## 本次修改

- 普通监测查询改用 `monitor.browse()`，只计算结果并存入进程内临时缓存，不调用磁盘归档。
- 临时缓存最多16个视图、64MiB序列化内容，每个视图有效期30分钟，超限淘汰最早的视图；仅保留筛选后订单的当日事实和依据，不保留完整输入及完整计算契约。
- 临时视图编号以 `live-` 开头。视图与依据按同一冻结结果读取，防止导入修订后依据串到最新版本。
- 已过期、被淘汰或服务重启后的临时视图返回410，页面显示“请刷新监测页面后重试”；刷新会按当前条件重新计算，不要求重新导入表格。
- 原有磁盘历史编号仍通过原仓库读取；内部 `create()` 仅保留为明确归档的兼容操作，普通HTTP查询不可调用它。
- 不改动利润公式、导入版本保存、正式订单写入及登录验证。没有删除已有历史数据。

## 验证

- 修复前，新增HTTP回归测试复现了只读查询新增磁盘历史的问题；修复后通过。
- Node20全量测试：170项通过，0失败；运行包已重新构建。
- 直接使用现有16个订单及构建后的运行包，执行100次查询（不同日期、窗口及订单筛选）、10次依据查询，再读取旧归档及其依据。
- 数据目录前后均为6610个文件、985955346字节，文件数量和容量增量均为0。
- 同时验证缓存容量、过期、修订后的依据冻结、跨视图依据拒绝访问及旧历史跨重启读取。
- 本地8787服务已重启加载新运行包。

## 后续注意

这次修复阻止继续因浏览生成历史，已有约940MiB数据仍保留。若要缩小现有目录，应另行制定备份和历史清理规则，不能直接删除被旧视图引用的快照或共享输入。后续真实导入和有意归档仍然会按业务需要增加数据；不要把普通查询再次接到 `create()` 上。
