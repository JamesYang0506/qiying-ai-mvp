## 2. 关键改动

1. 监测刷新不再读写 `b-module/b-state.json`。视图、快照和按内容摘要共享的输入分别写入 `monitor-state/views`、`snapshots`、`inputs`；快照只保存 `inputRef`，相同输入不重复复制。视图最后原子发布。
2. 逐日核算只构建一次日期索引，趋势按天累计；监测和单笔趋势复用同一逻辑。`evaluate()` 仍独占利润公式和可见性语义。
3. 计算缓存按修订、日期、基线等键区分，LRU 上限 64 项；同一键的并发请求共用进行中的 Promise。
4. 导入订单按 `sha256(orderId + revisionId)` 定位版本文件，启动扫描一次，之后只解析新增或变化的文件；外部新增、删除、修改会通过 mtime/size 失效。
5. 单笔分析先渲染 analysis，再独立加载趋势；portfolio 只在“明细数据”中的“同日可比订单”区打开时请求。新范围会中止旧请求，序号继续阻止迟到响应覆盖页面。
6. 监测页面使用 AbortController 取消旧查询，保留 250 ms 搜索防抖。

## 3. 性能结果

环境：Windows 11、24 CPU、Node v24.17.0。数据：16 个本地导入版本、16 笔订单、7,335 行；隔离临时目录，未在真实 `data/` 造单。命令统一使用 `--quick`（预热 1 次、正式 5 次、跳过历史复制），这是按“简化基准测试、缩短时间”的要求采用的快速口径；完整历史因旧实现追加时触发 V8 `Invalid string length` 而中止。所有数字单位为毫秒。

### 3.1 16 笔 / 16 天前后对照

| 场景 | 改造前 p50 / p95 | 逐日复用后 | 存储索引后 | 验收复测 |
|---|---:|---:|---:|---:|
| monitor | 2639 / 2906 | 267 / 279 | 262 / 271 | 267 / 269 |
| analysis | 71 / 86 | 33 / 38 | 15 / 24 | 14.5 / 15.2 |
| trend | 264 / 285 | 31 / 36 | 14 / 22 | 15 / 16.4 |
| portfolio | 1030 / 1209 | 1124 / 1197 | 61 / 80 | 60 / 63 |
| view | 56 / 71 | 63 / 72 | 28 / 30 | 28 / 30 |
| evidence | 46 / 61 | 45 / 48 | 27 / 46 | 16 / 17 |
| monitor 每次 evaluate | 272 | 16 | 16 | 16 |

监测端到端 p95 从 2906 ms 降到 269 ms，达到“16 笔、16 天、p95 ≤ 1 秒”的目标。单笔日期切换首屏由 analysis + trend 组成，复测约 30 ms，低于 500 ms。

### 3.2 订单数与趋势窗口

| 场景 | monitor p50 / p95 | analysis p50 / p95 | trend p50 / p95 | portfolio p50 / p95 | evaluate/次 |
|---|---:|---:|---:|---:|---:|
| 16 笔、16 天 | 267 / 269 | 14.5 / 15.2 | 15 / 16.4 | 60 / 63 | 16 |
| 50 笔、16 天 | 2747 / 3235 | 36.7 / 51.7 | 15.1 / 21.2 | 701 / 724 | 50 |
| 100 笔、16 天 | 6738 / 6954 | 58.5 / 66.5 | 40.4 / 43.5 | 1547 / 1589 | 100 |
| 16 笔、30 天 | 284 / 300 | 15.3 / 16.8 | 13.9 / 17.1 | 77 / 85 | 16 |
| 16 笔、90 天 | 318 / 326 | 14.9 / 17.4 | 14.8 / 17.4 | 63 / 76 | 16 |

50/100 笔监测超过 1 秒，主要成本是每笔订单一次完整 `evaluate()`（100 笔时单笔 analysis 已约 59 ms），加上 8.5 MB 响应和快照写入。16 笔目标场景已达标；本轮未继续压缩单笔核算成本。30/90 天窗口受订单自身生产周期限制，示例订单仅 4 天，窗口增大后趋势耗时基本不变。

### 3.3 100 次同范围刷新

16 笔、16 天，预热 1 次后连续刷新 100 次：

| 指标 | 结果 |
|---|---:|
| monitor p50 / p95 / max | 1017 / 1095 / 1124 ms |
| 共享输入对象 | 16 个，102 个视图后不增加 |
| 视图 / 快照 | 102 / 1632 |
| monitor-state 总量 | 401,706,882 字节 |
| 100 次新增持久化 | 390,681,800 字节，约 3.9 MB/次 |
| evaluate 总数 | 1600，即 16 次/次刷新 |

输入对象按内容摘要复用，数量固定为 16；每次刷新仍会新增 16 个不可变快照，因此持久化大小随历史线性增长。刷新后期 p95 约 1.1 秒，是保留不可变证据的预期代价；若需要更低延迟，应另立任务评估快照压缩或历史归档，不能删除旧证据。

## 5. 历史迁移状态与恢复

迁移工具：`node scripts/migrate-monitor-history.mjs --source <b-state.json> --target <monitor-state 目录> --backup <备份目录> [--dry-run] [--prune]`。

- 支持先 `--dry-run`、正式迁移强制备份、幂等重跑和中断续跑；备份包含 `manifest.json`（SHA-256、大小、数组数量）和导入版本副本。
- 迁移前逐条校验引用；`--prune` 只移除已完整迁移且仅属于导入监测的副本，先写临时文件再原子发布。
- 当前真实 `data/imports/b-module/b-state.json` 为 437,406,371 字节，**尚未迁移**。按既定约束，执行迁移和 `--prune` 需要明确授权；本轮只在合成临时数据上验证。
- 在迁移完成前，旧 `b-state.json` 中的历史视图仍保留在磁盘，但新的监测接口只读取 `monitor-state`，因此旧视图不能通过新接口访问。当前 `monitor-state` 中的 6 个视图是改造后新生成的视图。
- 恢复步骤：停止服务 → 用备份目录覆盖 `b-module` 与导入版本 → 如需回退代码，检出上一提交 → 重启。迁移不会自动删除原 `b-state.json`；没有 `--prune` 时原文件保持不变。

## 6. 已知限制

1. 50/100 笔监测未达到 1 秒；1 秒目标只针对 16 笔、16 天场景。
2. 每次监测刷新新增约 3.9 MB 不可变快照，历史线性增长；不做自动清理。
3. AbortController 只停止前端等待，服务端已开始的计算不会中断；后端仅合并相同缓存键的并发计算。
4. 计算缓存为进程内 LRU，最多 64 项，重启后冷启动；`knownAt` 变化会产生新键，不跨信息截止时间复用。
5. 趋势窗口受订单生产周期限制，30/90 天场景在本数据集上不能代表长周期订单。
6. 真实历史迁移、旧视图切换和 `--prune` 待授权执行。
7. 本轮未推送、未合并 `main`，未改动 AI 模块。

## 7. 结论

监测历史整体读写、逐日重复核算、导入全量扫描和前端等待四个主要瓶颈已消除。16 笔、16 天的监测与单笔首屏目标均已达到；50/100 笔和 100 次刷新的实际结果、代价和后续选项已记录。功能回归、契约和 A011 案例通过。真实历史迁移是剩余的运维步骤，需先备份并获得明确授权。
