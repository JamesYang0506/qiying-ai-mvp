# B模块 多订单与时间管理

## 目标与所有权

B负责同一天多笔订单的数据进入、持续更新、统一快照、列表和趋势。B拥有数据库、导入批次、费用池、基线与结果持久化；调用A得到核算结果，供网站和C使用。B不依赖AI才能完成更新。

## 数据组织

建议逻辑表：orders、order_revisions、baseline_versions、daily_reports、daily_report_revisions、manufacturing_pool_versions、calculation_jobs、order_snapshots、snapshot_sets、snapshot_set_entries、evidence、import_batches。表名可调整，职责不可重叠。

- 一个order_id跨天保持稳定。
- 日报采用“整份报告修订”语义：一份日报对应订单＋业务日期＋report_key，记录其规范化actual_input与完成数量；同一天多产线使用不同report_key。修改是整份替换新revision，不能再当新增累加。
- source_system＋source_record_id全局稳定去重；不同来源同一业务记录冲突进入核查，不自动叠加。
- 订单主档与预期基线也保存revision/不可变版本；历史查询不能把今天改过的数量、状态或基线套在旧日报上。
- 全部原始记录有business_date、recorded_at、revision、source_refs；DB迁移由B维护。

日报字段actual_input是当日归集资料，不是客户端自行计算的利润。累计核算由B按原始数量/单价/折扣/计件等记录归并、按适用阶段规则选取材料与制造分摊，再交A计算。制造池分摊每个pool_version_id只能在一个订单核算范围中纳入一次，不能将整月分摊金额在每一天重复扣除。

## 同一天批量处理流程

1. 客户端提交日报批次及Idempotency-Key；每条带source主键、report_key、expected_revision。
2. B预校验所有订单、字段与修订号。首版只支持atomic=true：任一记录校验/版本冲突则全部不写入，返回条目索引和原因。
3. 事务写入有效新版本和重算任务/事务outbox；相同内容重复提交返回原batch_id，不再新增日报。
4. B识别受影响订单、业务日期及共享费用池；按依赖选取一致的输入/基线/费用池版本。
5. 调A核算并保存新snapshot_id；发布当前快照指针前核对input_revision_set，旧任务若被新修订超越则superseded，不覆盖最新结果。
6. 批次状态accepted→recalculating→completed/failed；失败保留数据与原因，可重试同一任务，不重复写日报。

订单之间可并行核算。同订单/同版本只执行一次；初期可用单队列或每订单锁。数据量、时延目标待采样后约定，首版不承诺未经实测的并发容量。

## 时间推进、补录与修订

每日推进生成新日期快照，历史不覆盖。补录或修改D日记录后，重算D日至最新日期的累计结果以及依赖该记录的当日结果。基线修订按生效范围触发重算，旧snapshot_id仍可查询。

共享月制造费用池M、H或订单工时变化，影响该池的所有订单，不能只重算上传的那一笔订单。B保存依赖索引pool_version_id→order_ids→snapshot_ids。

查询区分：

- `as_of`：业务截至日期。
- `known_at`：当时已录入信息的截止时间；省略时在创建view时冻结为服务端当前时间，不在翻页时再次刷新。
- `period_start`：趋势展示起点；累计值仍从订单开工日归集，不误解释为区间累计。
- `view_id`：跨订单、跨日期的固定数据清单。固定订单集合与每个日期对应snapshot_id，记录缺失快照；列表、汇总、趋势和AI复用该view_id。

没有D日报时，不能默认为停产；若明确停产，应有确认的零产量日报。缺昨日记录时较昨日变化为null。快照重算未完成时展示pending/stale，不将旧版本称为最新。

## 汇总与趋势规则

按相同币种、利润类型、税/收入/成本口径分组，不能直接合并不兼容组。返回groups；界面必须选择某一组或分别展示。

每组known_actual统计实际可核算订单；comparable统计可与计划对照的订单。分别提供order_count、known_count、comparable_count、excluded_count及排除原因。实际毛利汇总ΣGP；汇总毛利率ΣGP/ΣR；偏差只对comparable集合求和。不可比订单仍在列表中显示。

趋势每个点包含date、actual_profit、expected_profit、delta、included_count、excluded_count。纳入集合变化必须显示覆盖变化，不将其全部解释为经营变动。跨日比较须使用双方都具备完整、同口径数据的交集，并返回excluded_count；当日毛利来自当日核算，不简单用两个不同覆盖的累计和相减。

## HTTP接口

下表均省略 `/api/v1` 前缀；具体字段见OpenAPI。

| 接口 | 用途 |
| --- | --- |
| POST `/orders` | 建立订单主档，初始expected_revision=0，返回order_id/revision |
| PUT `/orders/{order_id}` | 乐观锁修改主档，生成新revision |
| POST `/orders/{order_id}/baselines` | 保存完整预期输入及生效范围，产生baseline_id |
| POST `/reports/batches` | 同日/多日多订单日报批量写入，返回batch_id/job_id |
| GET `/reports/batches/{batch_id}` | 查询写入和重算结果 |
| POST `/manufacturing-pools` | 创建/修订费用池版本，返回pool_version_id、revision、job_id并触发依赖订单重算 |
| POST `/orders/{order_id}/recalculations` | 请求指定日期范围重算，返回job_id |
| GET `/jobs/{job_id}` | 查询queued/running/completed/failed/superseded与结果引用 |
| POST `/portfolio/views` | 冻结筛选及历史可见范围，返回view_id |
| GET `/portfolio/views/{view_id}` | 查询分组汇总和分页订单，next_cursor稳定 |
| GET `/portfolio/views/{view_id}/trend` | 返回该固定视图的每日/累计趋势 |
| GET `/orders/{order_id}/snapshots` | 按as_of/known_at查历史版本列表 |
| GET `/orders/{order_id}/snapshots/{snapshot_id}` | 取不可变CalculationResult；校验订单关系 |
| GET `/orders/{order_id}/reports` | 按业务日期与known_at取日报及来源 |
| GET `/snapshots/{snapshot_id}/evidence` | 为网页与AI提供证据明细 |

分页cursor绑定view_id、sort和page_size；客户端不能换过滤条件后沿用旧cursor。默认50、最大100；排序同值按order_id稳定兜底。日期start/end均包含边界。

## 独立开发与验收

B可先保存examples/calculation-response.json中的结果，不必等待A；随后替换为A.calculate_order。覆盖同日报两单、同键重试、同键不同内容、两人同时修改、补录、跨月费用池、基线修改、生效日期回放、未完成重算、分页期间更新、缺日报、不同币种组、最新指针防旧任务覆盖。

固定时间案例：16日补录12日记录后，当前视图12日至16日重算产生新快照；known_at=13日的历史视图保持原数据。涉及共享费用池时，第二笔未直接编辑的订单也必须刷新。
