# 公共数据与版本约定

本文件为三个模块的共同边界；字段结构以 `contracts/openapi.json` 为机器可读准则。路径前缀 `/api/v1`，业务日期采用 Asia/Shanghai，ISO 日期 `YYYY-MM-DD`；录入与计算时间为带时区 ISO 8601 时间。

## 一、数值与缺失

| 内容 | API 表示 | 说明 |
| --- | --- | --- |
| 总金额 | 十进制字符串，如 `"1320.00"` | 币种由 scope.currency 给出；用 Decimal 核算，按分入账 |
| 单价、数量、工时 | 十进制字符串，如 `"0.125000"` | 保留最多6位小数，单位单列 |
| 比例 | 小数字符串，如 `"0.132000"` | 13.2%；前端自行格式化，不传13.2冒充小数 |
| 百分点差 | 同样用比例差，如 `"-0.068000"` | 前端显示−6.8个百分点；不是相对下降34% |
| 未知 | null＋issues 中的原因 | 不传空字符串、NaN、Infinity或“待补齐”代替数值 |
| 已确认不存在 | `"0.00"`＋来源/确认记录 | 0与缺失严格不同 |

结构校验只保证格式；A 仍校验数量、单位、范围和数值约束。负折扣、负单价和负计件数量拒绝；材料退料通过明确净耗用规则处理，不能偷偷以负记录抵消不合法输入。

## 二、对象身份

- `order_id`：稳定内部主键，业务订单号另存 `order_number`；不能用款号代替订单主键。
- `record_id`：原始记录的稳定内部ID；`source_system + source_record_id` 为导入去重键。
- `baseline_id`：不可变预期基线版本；修订产生新ID，B记录生效范围。
- `snapshot_id`：某次核算的不可变结果ID；包含输入引用、公式和规则版本，不原地覆盖。
- `snapshot_set_id`：跨订单一致视图ID，保存 `{order_id: snapshot_id}` 清单、筛选条件与数据截止；多订单图表及AI用同一清单。
- `pool_version_id`：共享制造费用池版本；相同池修订必须影响所有参与订单。
- `evidence_id`：证据ID，与 snapshot_id 绑定；C 不能用其他版本的证据解释当前结果。
- `input_hash`：B对规范化输入计算的摘要；排序、空值和小数规范固定，A也可核验。

不可变版本记录 `effective_date`（业务生效日期）、`recorded_at`（系统收到时间）。示例：10月16日补录10月12日材料，当前重算12日至16日；回看“10月13日当时已知”不得包含这条16日才录入的资料。

## 三、核算范围 Scope

Scope 明确 `basis`（order_total/cumulative/daily）、`period_start`、`period_end`、`quantity_basis`（completed_good/settled/contract）、`quantity`、`quantity_unit`、`currency`、`tax_basis`（exclusive/ignored/unconfirmed）、`cost_scope_id`、`revenue_basis`（contract/production_equivalent/recognized）、`settlement_state`（open/completed/settled）。

生产等价收入 `production_equivalent` 只用于同阶段管理试算，不能称为财务已实现收入。已确认可比时，预期与实际必须共享完全相同的数量、期间、税和费用覆盖；B需按工段、固定费用及阶段规则提供预期输入，不能默认所有整单费用随产量等比例缩放。

scope 里将“已完工”与“已结算”分开。未结算也可以提供阶段毛利，但最终利润仍为待定。

## 四、结果状态与证据

`quality`：complete（当前核算口径完整）、estimated（有明确试算依据）、incomplete（关键值缺失）、invalid（逻辑或范围不合法）。它描述数据质量，不等于风险等级，也不代表审计认可。

`risk.level`：better/normal/attention/key/severe/not_applicable；UI分别显示优于计划/正常/注意/重点/严重/不可评级。缺资料通过 quality 和 issues 表示，不以 normal 代替。

每个 Evidence 至少包含 evidence_id、snapshot_id、order_id、metric、value、baseline_value、difference、unit、source_refs、rule_id、trust_status、occurred_at。source_refs 定位稳定记录ID及可选工作表/单元格。`trust_status` 为 verified/pending/anomalous/missing；规则校验通过不等于会计审计。

## 五、统一响应与错误

成功响应：`{schema_version:"1.0",request_id,data}`；分页数据再包含 items、next_cursor、view_id。错误响应：`{schema_version:"1.0",request_id,error:{code,message,details,retryable}}`。issues 是业务缺资料，结构错误是HTTP错误，两者分开。

| HTTP | code 示例 | 使用场景 |
| --- | --- | --- |
| 400 | INVALID_REQUEST | 日期、枚举或JSON结构不合法 |
| 404 | ORDER_NOT_FOUND / SNAPSHOT_NOT_FOUND | 对象不存在 |
| 409 | VERSION_CONFLICT / IDEMPOTENCY_CONFLICT / SCOPE_MISMATCH | 乐观锁冲突、同幂等键不同内容、跨版本混用 |
| 422 | INVALID_INPUT / ALLOCATION_INVALID | 负数、无效单位、损耗率不合法、费用池分母矛盾 |
| 429 | AI_BUSY | 本地生成队列已满，返回Retry-After |
| 503 | MODEL_UNAVAILABLE | 未连接模型、模型不可用 |

缺人工单价导致利润为null，可返回200＋quality=incomplete；不能用500表示正常的业务缺失。

写入使用 `Idempotency-Key`（最多128字符）和对象 `expected_revision`。同键同内容返回原结果；同键不同内容409。调用方遇超时须用原键重试或查询任务，不能随机新建键导致重复写入。

## 六、A与B的内部接口

语言无关签名，Python实现可用同名函数及类型对象：

```
allocate_manufacturing(request: AllocationRequest) -> AllocationResult
calculate_order(request: CalculationRequest) -> CalculationResult
```

AllocationRequest 包含完整费用池及各订单工时；A返回分摊结果及剩余待归属金额。B负责存储和事务，A不访问数据库、系统当前日期、网络或本地模型；相同输入与版本得到相同结果。

CalculationRequest 包含 server 分配的 snapshot_id、业务范围、预期输入、实际输入、明确的规则版本和证据来源。请求不接收“已有毛利答案”作为输入；A独立计算。HTTP `POST /profit/evaluate` 是无持久化计算，正式保存由B的计算任务完成。

## 七、前端接口边界

现有 `dist/data.js` 替换为HTTP适配层；`dist/metrics.js` 只保留演示模式，不对正式后端结果再次计算毛利和风险。前端只格式化数字、管理查询与展示，不把金额回传给AI作为权威事实。

所有模块通过相对路径 `/api/v1` 调用统一网关。C访问本机模型的地址只放后端配置；远程网页的localhost是访问者电脑，不能将已托管网页直接连接开发者本地Ollama。首版建议前端和三个模块在同一台本地应用服务器运行；共享在线版本另行配置服务器与鉴权，不将本地模型端口直接对外暴露。
