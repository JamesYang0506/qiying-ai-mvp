## 3. 问题清单与优先级

### P0-A：差距位置被写成确定的经营原因

**现状：** `dist/imported-workspace.js` 的 `renderImportedDiagnosis()` 将材料耗用、人工、能源等合并为“生产损耗与工艺”，直接输出“差距主要来自生产损耗与工艺”。说明还固定写“不良品也计工”“实际采购单价高于理论报价单价”。

**影响：** 材料耗用增加还可能与重量、领退料、口径或记录有关；人工超额也可能来自工价、归属或计件量。当前差额本身不能证明工艺问题，更不能证明不良品按何种规则计工。

**修复目标：**

- 将事实结论改为“差距主要体现在材料耗用与人工等生产成本”等与数据相符的表述。
- 对每个项目按正、负、零、未知分别生成描述。正值表示增加差距，负值表示抵消差距。
- 将可能原因放入“建议核查”，附可见日期、修订和证据，不输出已经确认的浪费、低效率或工艺故障。
- 保留最多三条有效建议，不为了凑数量生成无证据原因。

**验收：** 材料价格影响为负时应说明节省/抵消，不得仍写单价高于理论；仅人工增加时不强行归因为材料或工艺。

### P0-B：未知结果显示绿色勾号

**复现：** 将 `bridge.total` 设为 null，诊断标题为“差距原因待补齐”，但外层仍生成 `diagnosis-verdict ok` 和 `✓`。

**影响：** 文字表达未知，视觉表达正常，用户容易误认为订单安全。

**修复目标：** 独立处理 pending/incomplete、存在差距、达到理论三种状态。未知使用中性色和等待标记，不渲染正常勾号。基线或归因组件缺失时保留 null，不使用 `??0` 将其解释成零贡献。

**验收：** 未知不能显示“正常”“达标”或绿色确认；实际数据已知但基线未知时，应分别展示实际值和不可比较原因。

### P0-C：净差距占比可能超过100%，缺少抵消解释

**复现：** 耗用增加200元，材料价格节省100元，净差距100元，页面显示耗用“占差距200.0%”。

**说明：** 这是净额分母下的数学结果，不应简单裁剪成100%；问题在于当前页面没有解释增支和节省的抵消关系。

**推荐修复：**

- 展示“增加差距的项目”和“抵消差距的项目”，保留各自金额与净差距。
- 如显示主因占比，以完整的正向增支合计为分母并明确命名“占增支”；节省项目单独列金额。
- 预算允许损耗和舍入调整分别列为基线调整/舍入，不命名为生产原因。
- 主因判断若保留现有60%等阈值，应写入规则说明与版本，不将其描述为企业已确认的风险标准。

**验收：** 200元增支−100元节省＝100元净差距；正向项目占增支合计100%；缺项时不给完整占比；理想和预算模式均保持金额闭合。

### P0-D：利润安全线的名称、模型假设与实现位置

**现状：** 前端使用预算理论毛利/收入作为毛利率线；不良率线通过损耗预算÷材料及人工单位成本推算允许额外加工量，再换算比例。参考 `renderImportedDiagnosis()` 中 `unit`、`allowed`、`allowedRate`。

**评审判断：** 该不良率值是成本模型的推算结果，不能直接当作质量检验标准，也不能仅因不良率越线就断言实际利润已经跌破毛利率线。本轮没有判定某个具体阈值数值必然错误，要求的是解释假设、分开状态并统一规则来源。

**修复目标：**

- 在没有业务确认前，使用“预算模型参考阈值”，不称为已核定的企业安全底线。
- 毛利率参考线和不良率参考线分别提示；任一未知时显示具体原因。
- 展开项显示公式、参数来源、单位、基线版本、规则版本及适用条件。
- 缺材料/人工成本、收入或数量为零时不推导阈值；不得以缺失为零缩小分母。
- 将参考阈值、状态判断和规则版本放到服务端，使用 Decimal，前端只展示。
- 不修改已确认的核心利润公式。若要升级成正式质量阈值或剩余产量预测，需要另外的业务定义和验收案例。

**验收：** 服务端结果和页面一致；不良率越线与毛利率越线独立显示；未知、零分母、参数缺失、临界相等、预算为零及舍入边界均有测试。

### P1-A：首页仍是演示数据，定稿设计尚未落地

**现状：** `dist/app.js` 的 `monitoring()` 使用旧演示适配层，关注订单按累计风险/预期差额选取。用户已导入订单在另一工作区，尚未构成统一首页。

**修复方向：** 执行文档03的 H0–H5：已导入多订单、今日恶化优先、蓝白配色、实际/同进度理论趋势、当日毛利率分布及联动核查建议。单订单已有的“概览”和成本环形图不能替代多订单首页。

**必须保持：** 相同集合的金额对照，缺昨日不比较，累计差距增长不直接判今日恶化，补录变化与经营变化分开，前端不汇总金额。

### P1-B：差距下钻仍有断点

**现状：** 日期明细通过 `.slice(0,30)` 仅展示最近30条；“查看当天记录”只改变日期，未保留材料/费用项目定位；原始表隐藏了记录ID、关联ID和来源单元格。

**修复方向：**

- 用分页或“加载更多”访问所有日期，不只显示最近30条。
- 点击材料价格/耗用直接进入该日材料记录；人工/能源等定位费用类别和项目。
- 默认页面保持简洁，增加“查看来源”展开项，包含记录ID、文件角色、工作表、单元格和关联生产记录。
- 返回首页或上一层时恢复日期、基线、修订、项目、筛选及选中订单。

**验收：** 超过30条时最早记录可访问；补单可以追到关联生产；材料下钻不会默认停留在生产表；路径中的版本一致。

### P2：图表表达与可用性

- 成本环形图目前包括生产与经营费用，明确标题为“已归集生产及经营费用”，或将两类分组显示。
- 图例常驻金额及比例，悬停作为补充；缺项时说明占比基于已知项目，不声称完整成本构成。
- 图表提示支持键盘焦点和触摸查看，不只监听鼠标移动。
- 测试窄屏、长名称、较大金额与负值；减少小字号说明，避免图表缩小后标签难读。

## 4. 可复用的最小复现

在项目根目录使用 Node.js 执行以下合成样例，无需上传或修改本机案例：

```javascript
import {renderImportedDiagnosis} from './dist/imported-workspace.js';
const budget={theoreticalTotal:{revenue:'1000',gross:'200',material:'800',labor:'100',reserve:'30'}};
const sample=(total,components)=>({
  order:{quantity:'100'},
  cumulative:{processed:108,defects:8,actual:{margin:0.1}},
  bridge:{total,components}
});
const offset=renderImportedDiagnosis(sample('100',{
  materialUsage:'200',labor:'0',materialPrice:'-100',energy:'0',
  otherManufacturing:'0',otherProduction:'0',rounding:'0',budgetAdjustment:'0'
}),budget);
const unknown=renderImportedDiagnosis(sample(null,{
  materialUsage:null,labor:null,materialPrice:null
}),null);
console.log({
  netShare200:offset.includes('占差距 200.0%'),
  negativePriceWrongText:offset.includes('实际采购单价高于理论报价单价'),
  unknownGreenCheck:unknown.includes('diagnosis-verdict ok')&&unknown.includes('verdict-mark">✓')
});
```

在评审版本三个值均为 true。修复后应通过语义回归断言，不只检查删掉某个字符串。已有正常样例也要保留；测试中的旧“工艺原因”和“安全线”固定文案须跟随更准确的业务语义更新。
