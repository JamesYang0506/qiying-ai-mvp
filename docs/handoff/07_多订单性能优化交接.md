# 多订单分析卡顿：性能优化交接

日期：2026-10-17。开发基线：`a750634`，分支 `codex/latest-integrated-baseline`。

本文交接已完成的诊断和后续开发要求，尚未实施代码优化。执行计划见 `../superpowers/plans/2026-10-17-order-analysis-performance.md`。

## 1. 问题和实测证据

用户新增导入 12 份表格后感觉分析卡顿。诊断时本地共有 16 个订单版本、16 笔订单，生产、材料、费用和补单合计 7,335 行。文件数量不等同于订单数量，以导入服务列出的订单和版本为准。

以下是在现有机器上用 Node.js 24 单次本地测量的结果；不是多轮 p95，也不是端到端浏览器耗时。基线测试使用 Node.js 20，两者勿混同。

| 测量项 | 结果 |
|---|---:|
| 全部原始导入 JSON | 3,212,045 字节，约 3.2 MB |
| 扫描并读取全部导入版本 | 24 ms |
| A011 完工日单次分析 | 17 ms |
| A011 全周期趋势 | 127 ms |
| 按当前方式获取每笔订单并计算汇总 | 246 ms |
| 16 笔订单、16 天监测，纯计算 | 214 ms、272 次 evaluate |
| 上述监测响应 JSON | 348,341 字节 |
| 上述刷新新建的快照 JSON | 3,890,129 字节 |
| `data/imports/b-module/b-state.json` | 345,921,583 字节；187 个视图、762 个快照 |
| 读取历史文件 | 466 ms |
| JSON.parse 历史 | 980 ms |
| JSON.stringify 历史一次 | 1,878 ms |

监测计算采样业务日为 2026-09-12，趋势窗口 16 天。正式性能验收还需覆盖最新订单结束日期、30/90 天窗口及不同订单数。

诊断没有修改计算代码、删除历史或调用会生成新视图的监测 GET 接口；计算在内存中运行，历史仅只读测量。

## 2. 根因和修改范围

### P0：监测历史整体重写

`server/monitor/overview.mjs` 的 `create()` 每次计算后都追加视图和所有订单快照；快照保存 `inputs`、`evaluation`、`previous`、`result`、`evidence`。同一订单原始数据被反复复制。

`server/orders/repository.mjs` 的 `transact()` 读取整个 `b-state.json`，解析后分别序列化修改前和修改后的完整状态，再写回全部内容。JSON 处理同步阻塞 Node 事件循环，影响其他接口；交易队列还会串行等待。证据接口先获取视图再读取快照，可能重复读取同一巨型状态。

必须将导入监测历史从正式 B 业务仓库中分离，改为按视图/快照访问。不要把整个正式 B 仓库替换成只有监测能力的仓库。

### P1：重复计算与重复读取

- `server/monitor/overview.mjs:45`：逐日调用完整 `evaluate()`；筛选发生在计算之后。
- `server/profit/trend.mjs`：每个趋势日期重新扫描订单开工以来记录。
- `server/monitor/overview.mjs:38` 使用 `evaluation.days`，当前计算结果实际提供 `daySummaries`，昨日查询总是退回额外计算。需确认完整昨日证据所需字段，不能仅替换属性名而丢失字段。
- `server/storage/store.mjs`：`get()` 也扫描所有订单 JSON；portfolio 循环中形成重复全量读取。
- `dist/imported-workspace.js:171`：单笔分析每次切换日期都等待趋势和全订单 portfolio，明细中的可比订单区未打开时也照算。
- `dist/monitor-workspace.js`：搜索、日期、筛选触发新计算；序号只阻止旧响应覆盖 UI，不能取消后端工作。

## 3. 改造目标和边界

先解决随使用次数不断增长的历史读写，再减少重复计算，最后优化页面等待。保持现有页面主要布局和对外接口，第一轮不引入数据库、模型或新前端框架。

必须保持：

- 实际利润只包含选定业务日期可见的数据；未来及迟录数据不能提前出现。
- 固定 viewId/snapshotId 的版本和证据保持不可变，新版本不能修改旧视图结果。
- `null` 不变成 0；合格产量、补单已含、不良损耗、ideal/budget 和金额舍入口径一致。
- 汇总和趋势继续使用原先的可比集合及共同可比规则。
- 16 笔本地导入数据、正式 B 的订单/报工/制造池/幂等记录以及旧证据链接不能丢失。
- 保留当前同源、会话令牌和静态目录隔离校验。

## 4. 模块对接约定

下列内部接口为拟定开发约定，当前尚不存在。若执行者发现现有结构不适合，先更新本文和计划中的对应名称，再实施。

### 存储与监测服务

新增 `server/monitor/storage.mjs`，导出：

```js
createMonitorRepository(directory)
// 方法均返回 Promise
repository.saveView({ overview, snapshots }) // 返回 overview；发布视图前须已保存全部快照
repository.getView(viewId)                  // 返回 overview；不存在返回明确 404
repository.getSnapshot(snapshotId)          // 返回固定快照；不读全部历史
```

建议目录 `data/imports/monitor-state/views/`、`snapshots/`、`inputs/`。不可变输入按内容摘要复用，快照只保存 inputRef；证据所需原文可独立读取，避免把整周期输入复制进每个快照。所有 ID 校验和路径解析必须阻止越界。

视图最后以临时文件加原子重命名发布，保证可见视图引用的快照均可读取。单进程并发写采用串行发布或同等机制，不以删除老视图解决容量问题。

`server/http/routes.mjs` 分别创建正式 B repository 和 monitor repository，注入对应服务。

### 计算层

新增 `server/profit/series.mjs`，导出：

```js
calculateSeries(dataset, { start, end, baselineMode })
// 返回与当前 trend() 相同的 points 数组
```

共用每日核算逻辑，按日期索引原始记录，并从开工日累计到 end，只输出 start..end。不能只累加窗口内成本。金额必须继续 Decimal 和现有舍入；可见性须按每个输出业务日判断，不能将最终日期可见记录回填到早期。

监测层在已按 knownAt 固定可见输入后使用同一计算逻辑。完整 analysis 仍返回既有结构；完整证据和诊断按需生成，不为每个趋势点重复生成。

### 导入存储

保留 `createStore()` 的 `get/listOrders/listVersions/listRevisions/commit` 对外签名。增加内部订单版本索引和文件缓存；启动时扫描一次，commit 成功后更新。其他进程或用户直接改变文件时，须明确处理文件新增、删除和同名修改的失效机制，不能无限复用旧值。

portfolio 一次读取选中版本集合，避免循环调用每次全量扫描的 get。

### 前端与 HTTP

保持 `/api/import-v1/orders/{id}/analysis`、`trend`、`portfolio`、`monitor`、`monitor/views/{viewId}` 及证据接口现有字段和错误语义。内部存储格式变更不要求页面改接口。

`dist/import-api.js` 方法增加可选第三参数 `{ signal }`；查询参数仍使用第二参数。`getImportedOrders/getRevisions` 可相应增加可选 options，旧调用仍兼容。

单笔分析优先展示 analysis；趋势独立加载；portfolio 仅在明细可比订单区需要时获取。展示按订单、日期、版本、基线绑定的加载/失败状态，不能把新日期主卡片与旧日期曲线混显。切换范围取消旧网络请求，并保留序号校验。AbortController 不能保证后端计算停止，后端仍需合并重复请求。

### 缓存

计算缓存按输入版本及摘要、业务日期、基线、公式/规则版本和可见记录集合区分；监测还要包含固定订单集合和影响结果的参数。默认 knownAt 随时间变化，不能简单以“相同日期”复用旧视图。优先复用计算产物，新视图准确记录此次 knownAt 和引用范围；只有完整上下文一致才复用 viewId。

同条件并发计算共用进行中的 Promise；失败后移除缓存项；内存缓存必须有数量/容量上限。输入、可见记录、公式或规则变化都要失效。不可变历史文件不随缓存淘汰而删除。

## 5. 历史迁移和恢复

1. 停止该工作目录所属网站服务，备份原始导入文件和整个 b-module；记录 SHA256、大小、数组数量及版本。
2. 新建独立输出目录，分批导出 `kind=import-monitor` 的视图及其关联快照，保留原 ID、版本、knownAt、业务日期和证据。旧共享快照先复制，禁止未经检查删除。
3. 导出带进度清单，重跑幂等；中断后从已校验记录继续。原 `b-state.json` 保持不变，迁移不在 HTTP 请求中自动执行。
4. 逐条检查引用完整性；所有已发布旧监测视图仍能取得相同结果及证据。正式 B 使用的快照不得因迁移失去引用。
5. 校验后切换读取新仓库。正式 B 文件可在维护命令中移除已完整迁移且仅属于导入监测的副本，先写临时新文件再原子发布；保留原备份和回退命令。
6. 不自动清空历史、不改变原订单版本、不把本地数据提交到公开仓库。

## 6. 验收和交付

功能：现有 107 项测试、中底案例四个验收日期、契约示例检查继续通过；增加迁移、并发、缓存失效、历史证据和快速日期切换测试。契约检查通过不代表真实接口可用，须另测 HTTP。

结构：监测刷新不再读写整个 b-state；重复刷新不复制整套输入；历史数量增加不导致单次查询扫描全部历史；一笔订单一个趋势窗口不再按输出日期调用完整 evaluate。

性能目标为待验收指标，不是已达到结果：同机 16 笔订单、16 天窗口，预热后监测端到端 p95 ≤ 1 秒；单笔日期切换首屏数据 p95 ≤ 500 ms；100 次同范围刷新后，共享原始输入对象数量不增加，新增持久化大小与基线首次刷新比较并记录。记录 30/90 天、重启冷启动和 50/100 笔隔离模拟数据结果，禁止在真实 data 中造测试订单。

每种场景预热 3 次、正式运行至少 20 次，记录 p50/p95/max、CPU/内存、接口响应字节、写入字节和计算调用次数。浏览器另测主卡片显示及切换日期体感；终端计时不能代替页面验证。

交付修改清单、性能前后对照、迁移日志和恢复步骤；构建并重启实际服务，检查旧链接与新版页面，再本地 Git 提交。未经新指令不推送、不合并主分支。
