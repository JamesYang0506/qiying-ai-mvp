交接日期：2026-10-17。本文中的 CC 指接手执行开发的助手或成员；本文没有向其他会话发送任务。

## 1. 项目目标及用户要求

项目为“企盈智擎”，服务于长周期订单的每日动态利润监测，最终同时监测大量订单。三人分别开发 A 单订单核算、B 多订单与时间管理、C AI 秘书，再整合到一个应用。用户目前负责 A 模块。

必须保持的业务原则：

- 整单预期理论目标固定；实际利润随当天已可见的生产和费用记录累计。不能在订单刚开始时提前展示完整模拟周期的实际利润。
- 对照同进度、同口径的理论利润，解释差距来源；累计实际毛利不等于已结算最终利润。
- 模拟数据可以一次导入完整周期，但历史界面只能使用截至选定日期已经可见的实际记录。
- 成本 Excel 保持纯粹，业务工作表为成本计算、订单信息、原订单用量、补单用量。每日生产、材料、费用在配套文件中。
- 补单如果已包含在加工量、实际净耗中，不再追加数量或扣除一笔“补单损失”。
- 缺失数据不能默认为零。零、缺失、暂估、停产、待补录必须区分。
- 保留计算公式及必要初始资料；真实企业工作簿、计算输出、模型资料不进入 Git。
- 开发完成一个可验证阶段后及时保存 Git。

## 7. 当前导入 API 与格式

已实现前缀为 `/api/import-v1`：

- GET `/session`、`/orders`、`/portfolio`。
- GET `/orders/{id}/revisions`、`/orders/{id}/analysis`、`/orders/{id}/trend`。
- POST `/previews`、`/previews/{previewId}/commit`。

写操作校验同源及会话令牌。预览在内存中保留 10 分钟，重启后重新解析；预览不写入业务数据。确认需要匹配摘要，缺项时需要明确选择保存待补齐版本。参数及响应以 `routes.mjs` 和 `dist/import-api.js` 为准。

成本模板 `A-ORDER-0.2`，命名 Table：`CostParameters`、`OriginalRecipe`、`OriginalSizePlan`、`SupplementEvents`。配套每日表的“每日生产”A4以 `AB-TIME-0.2` 开头，命名 Table：`DailyProductionCase`、`DailyMaterialCase`、`DailyExpenseCase`。缺少 Table 不猜测范围，原始输入公式不采用缓存值。

首版限制：单订单单核算子项、完整周期零期初、生产等价收入、模拟报价不拆税、Asia/Shanghai、已归属直接费用金额。是否模拟必须明确为“是”或“否”；首版不支持的口径会拒绝，不应绕过校验来导入。

规范化数据保存在 `data/imports/`，已被 Git 忽略。保存的是整套修订，不是将新上传的周期内容再次累加。业务修订使用新修订号，基线内容变化使用新基线号。原始 Excel 不长期归档，备份需同时保留原文件、该目录及对应代码版本。

## 8. 计算口径与标准案例

用户确认图片中的百分比均按 17.2 元/双报价计算；能源为 **0.4%**，不是 0.4 元/双。材料65%、生产管理2.8%、公司管理1.3%、行政1.7%；标准重量650g/双、合同100500双。缺乏企业凭证的人工、物流及每日变动参数仍是模拟假设，不可转成已核实的真实成本。

当前理论材料价格由报价材料占比与标准重量校准原表材料价格比例；实际材料为净耗×实际单价。生产毛利扣材料、人工、制造及其他生产；经营利润再扣管理、销售、财务。理想模式不含额外损耗预算；预算模式含生产及不良损耗预算，归因不重复扣损耗。

每项金额使用 Decimal；逐日舍入后累计与整单一次计算会有小差异，当前单独返回 `theoreticalRounding`。补单与不良数量不一致保留差异；不凭差异自动补造记录。

## 10. 下一位开发者需要关注的限制

这些是后续工作或待验证风险，不表示已经完成：

- 当前 `asOf` 同时约束业务日及可见时间；尚无独立 `known_at`、不可变计算快照或跨单固定 `view_id`。
- 当前只供本机单服务实例使用。尚无多人写入、登录权限、数据库事务及远程部署能力。
- 核算随查询重算，趋势逐日调用核算器；大量订单、长周期的容量尚未测量。还需验证极端数量、超大稀疏 Table、超长补录日期等边界。
- 本轮明确限制税口径及零期初。扩展前先定义数据模型和验收案例，不直接取消限制。
- 已导入订单汇总入口已有基础能力；主监测页仍以演示数据为主，尚未统一正式数据源。
- 当前归因属于成本差额解释，不等于生产管理上的原因已经核实。AI不能把“材料耗用增加”直接断定为浪费。
