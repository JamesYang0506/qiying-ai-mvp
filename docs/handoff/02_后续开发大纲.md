# 后续开发大纲

这是给 CC 和三位成员的建议路线，不代表下列功能已经实现，也不构成直接发布或变更业务口径的授权。建议按 P0→P1→P2→P3→P4 执行，每个阶段形成可演示结果并提交 Git。

## P0：接手核验与基线固化

**目的：** 确认接手的是本地新版，保留已验收结果。

1. 阅读交接文档，检查 Git 分支和未提交改动；保护 `data/imports/` 及仓库外案例。
2. 重建 runtime，运行测试和契约校验，复算中底案例四个日期。
3. 从标准 Excel 导入、确认、切换日期与版本、重启恢复走通一次，记录实际页面地址。
4. 整理“已实现/仅设计/待验证”清单，确认 A/B/C 责任边界。

**交付与验收：** 接手验证记录；原56项测试及中底案例结果保持不变。若基线失败，先定位原因，不叠加新功能。

## P1：A 模块完善——让单订单结果更易检查

**优先级最高，用户目前负责此模块。** 先完成可解释性和可维护性，再扩展公式范围。

### P1.1 计算与字段口径整理

- 将当前输入字段、单位、理论模式、费用类别、状态及缺项传播整理成可维护的数据字典。
- 明确区分整单理论目标、当日实际、累计实际、同进度理论、经营利润及未来结算字段。
- 对齐当前导入计算结果与 A 模块目标契约，列映射和差异；建立适配层，复用现有计算器。
- 区分实际资料、理论基线及进度各自的完整性，让结果和提示说明具体缺什么。

**验收：** 任一关键字段缺失时，相关结果为未知并有来源提示；已有完整案例金额不变；不存在两套重复计算公式。

### P1.2 导入体验与错误定位

- 显示生产、补单、材料、费用的预览数量及关键明细，不只展示生产行。
- 提供可下载的错误清单，包含文件角色、工作表、单元格、记录ID、错误原因和修正建议。
- 补充格式示例和清晰的标准模板使用说明；若提供模板下载，只包含空白或合成数据。
- 提示当前已保存版本、重复导入及冲突原因；防止用户把旧版本当作最新资料。

**验收：** 用户可以根据错误清单修复一份故意带错的合成文件并重新导入，不需要开发者查日志。

### P1.3 单订单核算可解释性

- 指标点击后展示数量、单价、净耗、费用构成、公式和来源单元格。
- 从差距项目下钻到对应日期及记录，展示价格和耗用影响的计算依据。
- 支持修订前后对照，明确“资料补录导致的变化”和“生产经营变化”。
- 核对毛利率差的百分点与相对下降；若接入风险分级，复用已确认规则并标识试算性质。

**验收：** 中底案例主要差距可定位到原始记录；归因合计与总差距精确一致；没有数据支持时只提示待核验原因。

**暂缓：** 非零期初、正式税务收入、多币种、预测完工利润。需要相应原始资料和独立验收案例后再扩展。

## P2：B 模块落地——多订单和时间版本统一

### P2.1 正式数据存储与接口适配

- 将原始记录、基线、修订及导入批次迁移到 B 拥有的存储模型，保留旧本地数据迁移/备份方案。
- 明确整套修订与逐日日报修订的转换规则，加入乐观锁、原子批次和内容幂等。
- 逐个落地目标 `/api/v1` 接口，保持旧导入入口可用并注明迁移状态。

**验收：** 重复提交不增量叠加；冲突不部分写入；迁移前后金额一致；失败可恢复。

### P2.2 历史快照与补录重算

- 分离业务截至日 `as_of` 和信息可见截止 `known_at`。
- 固定输入、基线和规则版本，保存不可变 `snapshot_id`。
- 补录 D 日资料后重算受影响累计结果，保留原快照；过时任务不能覆盖新版本。
- 为多订单查询建立固定 `view_id`，列表、汇总、趋势及后续AI使用同一集合与版本。

**验收：** 同一历史快照可重复查询；后来补录不会改变旧快照；新视图可以看到补录后的结果。

### P2.3 多订单主页面与容量测试

- 让已导入订单进入主监测页，提供明确的演示/导入数据来源切换。
- 汇总按同币种、同口径计算，展示可比与排除数量及原因；毛利率按总毛利/总收入计算。
- 支持批量导入状态、筛选、关注订单和同日对照。
- 用合成订单测量导入、重算、列表及趋势时延，按结果决定索引、缓存或任务队列。

**验收：** 页面各区域基于同一固定视图；缺项订单不消失，也不被当作零；容量报告给出实测环境和数据规模。

**后置扩展：** 共享制造费用池。先确认工时及费用资料，再实现全池分摊守恒和跨订单依赖重算。

## P3：C 模块落地——有依据的 AI 秘书

1. 接入可配置的本地模型适配器和服务状态；模型选择按设备资源实测，不在交接中预定具体型号。
2. 只读取 B 的固定快照/视图，提供订单、趋势、证据和规则的受限查询工具。
3. 先支持利润解释、当日简报、差距核查、缺失数据四类问题；回答金额由验证过的服务端事实提供。
4. 实现异步任务、失败提示、取消及上下文版本检查；模型不可用时明确提示。
5. 保存人工反馈，建立合成问答评测集；先评估提示、检索和工具是否够用，再决定是否训练。

**验收：** 回答的订单、日期、金额和引用一致；缺项会说明未知；原因建议标为待核验；不会改写订单数据或自行执行生产动作。

## P4：整合验收与团队交付

- 跑通“标准文件→B入库与版本→A核算→固定视图→网站/AI解释”的完整链路。
- 保留中底完整案例的本地核验；团队/CI使用可公开的合成数据。
- 完成跨模块契约回归、启动回归、数据备份恢复和失败恢复演示。
- 更新 README、接口实现状态、迁移说明及开发包，确认发布内容不夹带业务数据。
- 在用户明确授权的目标分支与发布方式下推送、合并或发布。

**验收：** 新成员按文档可启动并走通合成案例；同一视图中的页面、核算和AI金额一致；版本可追溯，回滚步骤可执行。

## 推荐给 CC 的首个执行批次

先做 **P0 + P1.1 + P1.2**。这一批的成果应是：接手验证记录、字段/口径字典、可定位的导入错误清单、四类数据预览，以及对应回归测试和 Git 提交。完成后再进入差距下钻与 B 模块，避免同时改动存储、公式和 AI 导致联调困难。
